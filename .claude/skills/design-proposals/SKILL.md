# デザイン修正フロー（提案アーティファクト → 選択 → 忠実実装）

デザイン変更は必ず **①現状把握 → ②複数案のアーティファクト提示 → ③選択 → ④忠実実装 → ⑤検証** の順で進める。
いきなり本番コードを触らない。**まずアーティファクトで案を出し、ユーザーに選ばせる**。

> ⚠️ 教訓（Bauhaus 刷新時）: **色だけ替えて構造を残すと「乖離」する。**
> 選ばれた案の見た目の核心＝**地色・書体の太さ・図形の質感・構図・モーション**まで丸ごと落とし込むこと。

## 1. 対象と狙いの確定
- 変更対象（全体／セクション／コンポーネント）と要望（何を・どう変えたいか）を一言で固定する。
- 曖昧なら `AskUserQuestion` で最小限だけ確認（対象・方向性・どこまで寄せるか）。

## 2. 現状ソースの把握（案は現行を基点に）
- 対象の現行マークアップ（`src/pages/**`・`src/components/**`）を読む。
- デザイントークン `tailwind.config.mjs`（`bauhaus.*`）・`src/styles/global.css`・該当 `specs/**` を確認する。
- 案には**実コンテンツ**（氏名・肩書き・スキル・経歴など実データ）を流し込む（lorem 禁止）。

## 3. 修正案アーティファクトを作る（必ず提示・ここが要点）
- `artifact-design` skill をロードして設計品質を担保する。
- **毛色の違う複数案**（規模に応じ 3〜6 案）を **1 枚の HTML ルックブック**にまとめ、`Artifact` で公開する。
  - 各案は配色・書体・構図・モーションを作り分ける。単一テーマに振り切った「ワールド」でも可。
  - 現行トークン/コンテンツを基点にしつつ、テンプレ的な既定デザインは避ける（毛色を意図的に散らす）。
  - CSP のため Web フォントは data URI か堅牢なシステムスタックで代替（実装時に実フォントへ置換）。
- **モバイルで見やすいこと（必須）**: ルックブックはスマホ（〜390px 幅）で快適に読めることを最優先にする。
  - ページ本体を横スクロールさせない。多段は狭幅で 1 カラムに畳む（`flex`/`grid` + `gap`）。
  - 相対単位・`clamp()`・`max-width:100%`。文字は狭幅でも十分な大きさ、行長は詰めすぎない。
  - はみ出す要素（表・コード・図・ワイドなモック）は各自 `overflow-x:auto` の器に入れる。
  - 各案パネルはモバイルで縦積みして 1 案ずつ大きく見せる。タップ領域は十分に取る。
  - 公開後、狭幅（例 390px）でも横スクロール・重なり・見切れが無いか確認する。
- 一覧表（案 No・毛色・一言）を添えて選びやすくする。狭幅では表もカード化するなど崩れないようにする。

## 4. 提示 → 選択
- ユーザーに提示して選んでもらう（掛け合わせ・追加案・別方向の要望にも応じる）。
- 必要なら `AskUserQuestion` で採用番号と「寄せ度合い」を確定する。

## 5. 忠実に実装（乖離させない）
選ばれた案を実ソース（Astro / React / TS）へ落とし込む。**見た目の核心を全部移す**:
- [ ] 配色：`tailwind.config.mjs` の `bauhaus.*` トークンのみ。パレット外の色を足さない。core 5 色の hex は不変（`specs/a11y.spec.md` のコントラスト契約）。`--c-accent = red` を維持。
- [ ] 書体：案の書体の太さ・幅・字間まで再現（必要なら `BaseLayout.astro` のフォント link と `font-sans` を差し替え）。
- [ ] 地色・構図：案の背景色・レイアウト・図形の質感（フラット/立体・大きさ・配置）まで一致させる。トークン連動でライト/ダーク両対応にする。
- [ ] モーション：`prefers-reduced-motion: reduce` で静止フォールバック。`transform` のみ・CLS ゼロ。
- SDD：先に該当 `specs/**`（無ければ新規）を更新してから実装する。designer→frontend の分担を使ってよい。

## 6. 検証
- `frontend-verify` skill、または `npx astro check` + `npm run build`。
- Chromium（Playwright）で**ライト/ダーク・モバイル幅**のスクショを撮り、選んだ案と並べて見比べる。乖離があれば直す。

## 7. 締め
- `specs` の受入条件（`- [ ]`）を検証する。コミットまで行う。push / PR はそのセッションの git ワークフローに従う。
